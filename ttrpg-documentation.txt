A. WHAT DOCUMENTATION TO WRITE AND WHY
==========================================================================

A professional portfolio should demonstrate analysis: why the product exists,
how ambiguous behavior was clarified, how decisions affect data and users, and
how outcomes can be checked. Document count is not a measure of quality. For
this project, use the following as sections of one coherent document.

A1. Business requirements / lightweight BRD
Purpose: explain the problem, intended value, objectives, and scope boundaries.
Write: background, current and desired situation, business requirements,
success measures, assumptions, constraints, risks, and exclusions.
Keep technical design out of business requirements: "retain session history"
is a business need; "SQLite" is a solution choice supporting that need.
Done when: each objective connects to a real owner need, scope distinguishes
current and future work, and unmeasured benefits are clearly marked.

A2. Functional requirements catalogue
Purpose: specify observable system behavior precisely enough to review or test.
Write: uniquely identified requirements grouped by session management,
campaigns, systems/colors, calendar, statistics, and import/export. Include
inputs, outputs, validation, error behavior, and dependencies where relevant.
Avoid vague wording such as "easy to use" or simply restating button labels.
Done when: each requirement has one clear obligation, status, source, and
acceptance coverage; uncertainties link to the gap register.

A3. Business rules catalogue
Purpose: keep domain rules consistent across screens, API behavior, and reports.
Write: session versus one-shot identity, defaults versus actual session values,
required data, archive/delete restrictions, color ownership, date semantics,
statistical grouping, and import classification/normalization rules.
Rules explain what must remain true; functional requirements explain what the
app does to enforce or apply those rules. Reference rules instead of copying
their wording into every story.
Done when: each rule has scope, source, examples and exceptions, and conflicts
between intended rules and implemented behavior are visible.

A4. User stories
Purpose: describe a user goal and its value in a small unit of work.
Write: "As the tracker owner, I want ..., so that ...", with linked requirements,
rules, acceptance criteria, and dependencies. One real actor is sufficient.
Use stories for each meaningful feature, especially future changes. Label
stories reconstructed after development; do not imply they guided the build.
Done when: a story describes an outcome, is reasonably bounded, and has
testable acceptance criteria. Do not invent administrator/player personas.

A5. Detailed use cases
Purpose: explain branching interactions where a short story is insufficient.
Write: goal, actor, trigger, preconditions, main flow, alternative/error flows,
postconditions, cancellation, and related requirements/rules.
Prioritize add/edit session, inline creation, and archive/delete. A simple
system rename does not need its own lengthy use case.
Done when: all meaningful branches end in an explicit outcome, including what
is or is not saved after an error or cancellation.

A6. Acceptance criteria and validation evidence
Purpose: define how to decide whether a requirement or story is satisfied.
Use Given/When/Then for state-dependent behavior; use checklists for field and
display rules. Cover normal, invalid, boundary, and failure cases as applicable.
Criteria describe expected results; tests describe how to check them; evidence
records what actually happened. These are related, not interchangeable.
Done when: criteria are observable, reference their requirement/story, and
separate expected behavior from actual results. "Not run" is a valid status.

A7. Data dictionary and ERD
Purpose: explain the information the app stores and how records relate.
Write: entity/field meaning, type, nullability, format, defaults, uniqueness,
relationships, source, validation layer, and anonymized examples. Distinguish
stored fields from derived display values and computed statistics.
Done when: systems, campaigns, and sessions are covered, relationships match
the code, and API/UI validation differences are identified.

A8. Non-functional requirements (NFRs)
Purpose: define measurable quality expectations and operating constraints.
Write: usability, responsive behavior, accessibility, data integrity,
persistence/recovery, performance, supported environments, and private access.
Separate agreed constraints from proposed targets and unverified properties.
Done when: each NFR has a measurement method, environment, and evidence status.
Do not claim accessibility compliance, recovery capability, or performance
levels based on appearance or configuration alone.

A9. Diagrams
Purpose: make boundaries, branching processes, relationships, and interactions
easier to inspect. Select diagrams by the question they answer (see section E).
Done when: every diagram has a title, scope, notation, legend where needed,
baseline/status, linked requirements, and consistent terminology.

A10. Traceability, decisions, risks, and gaps
Purpose: explain where requirements came from and prevent contradictory edits.
Write: a small cross-reference matrix; evidence-based decisions with rationale
and consequences; unresolved questions with resolution actions; prioritized
risks with mitigations. Missing historic rationale stays "unknown".
Done when: high-priority requirements can be followed from business need to
acceptance evidence, and open questions have a next action.

A11. Portfolio case study (later, concise)
Purpose: give employers an accessible entry point into the detailed work.
Write: problem, personal role, scope, two or three difficult decisions, selected
artifacts, observed outcomes, limitations, and lessons learned. Explain the
retrospective nature of analysis and AI assistance honestly.
Done when: claims are supported and examples are anonymized. Avoid invented
commercial impact, team roles, approvals, or measured time savings.

A12. Product documentation (deferred by owner)
Purpose: help someone use, install, and maintain the app. Typical outputs are a
user guide, setup guide, troubleshooting, known limitations, and release notes.
Do not draft these in the current documentation scope. The deployment-guide
item remains in the product backlog; recording that dependency is in scope.

B. BUSINESS CONTEXT, OBJECTIVES, AND SCOPE
==========================================================================

B1. Business problem and opportunity
The owner needed a convenient place to record TTRPG sessions, visually
distinguish campaigns, and review playing statistics. A previous calendar
workflow did not provide the desired campaign color differentiation or a
comfortable way to calculate statistics. The build plan also records a Notion
tracker/export as a migration source. The exact sequence of calendar and
Notion use is not established; do not invent it.

The intended outcome is a single manageable session history with calendar and
list views, reusable campaign defaults, and monthly/annual statistics. This
is a personal utility, not a commercial multi-user service.

B2. Draft business requirements and proposed success measures
These are reconstructed needs and proposed evaluation targets, not measured
results or historical commitments. Confirm targets when drafting requirements.

BR-01 Centralize reliable session history.
Measure: reconcile every record in an agreed reference dataset against stored
and exported data, including relationships and non-ASCII text; target 100%.
The plan records an initial 26-row import, not the current session count.

BR-02 Reduce repetitive entry while retaining control of actual session data.
Measure: an existing active campaign can be logged for today with one action
from its visible Quick Add card; edited flows preserve intentional overrides.
Target: all agreed scenario cases pass. No time-saving baseline exists yet.

BR-03 Make sessions visually identifiable and findable.
Measure: locate seeded sessions through calendar and list views and distinguish
campaigns using labels as well as color. Target: all agreed lookup tasks pass
at representative desktop and phone widths. Test conditions to be defined.

BR-04 Make monthly and annual activity understandable without manual counting.
Measure: compare counts, breakdowns, ran/played split, and longest gap with a
hand-calculated synthetic dataset. Target: exact agreement for defined rules.

BR-05 Preserve owner control of data and access.
Measure: complete manual exports contain all three entity types; persistence
and recovery require separate exercises. Private deployment is a documented
constraint, not a claim that the home-server setup has been verified.

B3. Current product scope (supported by source inspection)
- Sessions workspace: calendar and list, filtering/sorting, add/edit/delete.
- Campaign sessions, named standalone one-shots, inline campaign/system entry.
- Quick Add: Log today and an Edit action opening a prefilled form.
- Campaign management, archive/unarchive, guarded campaign deletion.
- System management and base colors; frontend-derived shades and suggestions.
- Custom date/month/year pickers; monthly and annual statistics.
- SQLite storage, startup seed import, manual JSON/CSV export.
- FastAPI serves API and frontend; Docker Compose configuration exists.
These are implemented-in-code observations, not new end-to-end test results.

B4. Planned product scope (from unchecked Future Additions)
- Generic Add Session defaults to Campaign session, today, no campaign selected.
  Today is already implemented; the type default remains one-shot in code.
- Quick Add redesign including Add with prefilled defaults but blank required
  date; card/actions design is still exploratory.
- Deployment guide and Docker volume persistence verification.
- Automatic timestamped backups or scheduled backup tooling.
- Reset/reimport administration for development/data cleanup.
- Backend tests for import, deletion guards, export and core API behavior;
  possible lightweight frontend tests later.
- Discussion of additional statistics; no specific new chart is committed.
The custom pickers and color-suggestion work under Future Additions are already
marked complete and have implementation/commit evidence; they are not future
features simply because of their position in the plan.

B5. Exclusions
Product: multi-user accounts, character/sheet management beyond a link,
reminders/notifications, native mobile app, recurring-session auto-scheduling.
Session time of day and campaign-session titles were explicitly dropped.
This delivery: implementation changes, full specifications, executed QA,
finished diagrams, user manuals, deployment, and public portfolio publishing.

B6. Constraints, assumptions, and risks
- Small personal project: keep one written source and selective diagrams.
- Date-only records; managed system names; GM remains free text.
- Local usage is recorded in history. LAN/Tailscale is the intended remote
  access model; no application login. Do not imply public hosting readiness.
- Dataset is expected to be small; browser-side statistics are the current
  design. Capacity and response-time limits have not been measured.
- Risk: retroactively documenting bugs as requirements. Mitigation: retain
  separate intended, observed, and proposed columns throughout.
- Risk: backup claims exceed demonstrated restore capability. Mitigation:
  distinguish export, automated backup, and tested recovery.
- Risk: changing forms and dates invalidate multiple artifacts. Mitigation:
  prioritize them first and maintain traceability to calendar and statistics.

D. PRIORITY AREAS AND INITIAL GAP REGISTER
==========================================================================

P1 = first documentation wave: high change frequency, core value, or data risk.
P2 = next: important supporting behavior and correctness.
P3 = later: future exploration and portfolio presentation.
These are documentation priorities, not a declaration that every gap is a bug.

D1. Session creation and editing -- P1, start here
Owner identifies this as the most revised area; commits and current branching
code support that assessment. Inventory every entry point: generic Add,
calendar day, Quick Add Log today, Quick Add Edit, and editing an existing row.
For each, record type/date/default values, editable overrides, required fields,
type/campaign changes, cancel, submit, deletion, error, and refresh outcomes.
Deliver: entry-point matrix, requirements, rules, stories, detailed use cases,
acceptance criteria, BPMN workflow, and one sequence diagram.

GAP-01 OBSERVED/PLANNED: generic Add defaults to one-shot, while future scope
requests campaign mode. Date already defaults to today. Resolve the intended
future behavior without rewriting the current baseline. Source: JS
openSessionDialog; plan Future Additions. Priority P1.

GAP-02 PLANNED: Quick Add has Log today and Edit; blank-date Add is absent.
Define actions, date requirements, and labels before modeling the future flow.
Source: renderQuickAdd, quickSaveCampaign, plan. Priority P1.

GAP-03 OBSERVED RISK: inline system/campaign creation uses separate requests
before saving the session. A later failure may leave a created entity behind.
Specify partial-success, retry, and cancellation expectations; validate with a
controlled scenario later. Source: saveSession/resolveSessionSystemId. P1.

GAP-04 UNRESOLVED: document whether switching campaign/type should overwrite
manually entered values; distinguish initial defaults from later changes and
editing existing sessions. UI applies link defaults, while backend
build_session falls back for GM/system but not link. Source: JS default helpers
and Python build_session. Describe each layer before deciding consistency. P1.

D2. Calendar, dates, and modal interactions -- P1
Owner identifies native pickers/calendar as difficult without prior knowledge.
The July bug report provides a concrete regression case. Cover date-only ISO
storage versus dd/mm/yyyy display, today, selected day/month, leap dates,
year/month boundaries, played-month jumps, dismissal, keyboard/focus behavior,
small screens, and short viewports. Define supported browser/device checks.

GAP-05 RECORDED FIX, NOT RETESTED: month arrows closed the picker; nested
scrolling complicated the modal. Include both in acceptance/regression coverage.
Source: ff43d63 and build task report. Priority P1.

D3. Data integrity, import, and exports -- P1
These determine whether session history is trustworthy even though the owner
did not identify them as the hardest development work. Draft the data
dictionary/ERD early as a dependency for session rules and statistics.

GAP-06 OBSERVED RISK: startup imports when no sessions exist and a seed file
exists. Existing systems/campaigns are not the startup guard. Investigate
restart after deleting all sessions, repeated import, partial import failure,
and uniqueness conflicts. Import commits in stages. Do not call it an
idempotent restore mechanism. Source: startup/import_seed_data. Priority P1.

GAP-07 RECORDED/UNVERIFIED: plan marks export complete but persistence check
open; automatic backup/admin tooling remain planned. Manual JSON/CSV export
endpoints exist; a restore procedure has not been established by this review.
Define fidelity and recovery criteria separately. Source: main.py/Compose/plan.
Priority P1 for documenting boundaries; operational execution comes later.

GAP-08 OBSERVED/UNRESOLVED: import identifies one-shots by a name substring,
not general recurrence count. Define approved classification and normalization,
including missing systems and GM aliases. Use a synthetic fixture; the plan's
26-row figure is historical, not freshly reconciled. Source: import helpers.
Priority P1.

D4. Campaign lifecycle and systems/colors -- P2
Cover archive versus deletion, archived campaign selection, defaults versus
historic actuals, unique names, color ownership and shade recalculation.

GAP-09 OBSERVED: archived campaigns disappear from Quick Add but remain in the
session selector with an archived label; backend does not prohibit logging
against them. Decide whether this is intended, then document explicitly.
Source: renderQuickAdd/populateCampaignSelect/require_campaign. Priority P2.

GAP-10 CONFLICT: early plan gives one-shots the base color; implementation
derives one-shot shades. A resolved-plan sentence also mentions a one-shot's
own color, but storage has no per-session color. Reconcile wording. Campaign
shade indices depend on name-sorted campaigns, so renaming/adding campaigns
can change shades; "stable" needs a precise definition. Source: color model,
models, campaignShadeIndex/oneShotShadeIndex. Priority P2.

GAP-11 OBSERVED RISK: backend system names are checked for duplicates before
trimming, and color values have no explicit hex-format validator. Define
whitespace/case/empty-input and validation expectations; distinguish source
risks from reproduced defects. Source: system create/update schemas/routes.
Priority P2.

D5. Statistics and business definitions -- P2
Core product value: document calculation rules, not just chart screenshots.
Cover period selection, one-shot grouping, session GM/system overrides,
empty datasets, ties, same-day sessions, and yearly boundary behavior.

GAP-12 OBSERVED: ran/played uses an exact hardcoded owner GM name, not a user
profile. Portfolio examples use DM1 as owner without implying configuration
exists. Define alias/case assumptions. Source: renderYearReview. Priority P2.

GAP-13 OBSERVED/UNRESOLVED: counts include all records in the selected period
without a completed/planned status. Longest gap compares adjacent dates within
that year's selected records, excluding year edges and cross-year gaps; fewer
than two records gives zero days. Confirm future-date and tie policies before
calling these universal business definitions. Source: statistics functions.
Priority P2.

D6. NFRs, remaining roadmap, and case study -- P2/P3
Document private-access assumptions, responsiveness/accessibility expectations,
representative dataset size, backup boundaries, and meaningful validation.
Keep automatic backups, admin reset tooling, and new statistics as separate
future items. Visual polish comes after rules and data definitions.

GAP-14 RECORDED: README still describes a Phase 1 foundation, despite later
features. Record the mismatch; rewriting product documentation is deferred.
Source: README versus plan/Git. Priority P3.

Gap resolution process: add evidence -> identify observed and desired behavior
-> record owner decision if needed -> update linked requirements/criteria ->
verify separately. None of these findings authorizes an implementation change.

E. DIAGRAM PLAN
==========================================================================

Diagrams are planned here; detailed drawing is a subsequent task. Keep each
small enough to read without tracing the entire application on one canvas.

DIA-01 System context -- first, a compact orientation sketch
Question: who uses the app, and where are its boundaries?
Show owner/browser, tracker, external seed/export files, and linked resources.
Label local usage separately from proposed LAN/Tailscale access. Links are
references, not integrations or automatic imports. Link BR-01 and BR-05.

DIA-02 BPMN: record or correct a session -- P1
Question: how does the owner reach a saved or cancelled outcome?
Show start, choose entry method/type, supply/review information, validate,
save or correct errors, and finish. Use Owner and Application lanes within
one process if helpful; lanes express responsibility, not extra stakeholders.
Keep inline creation as a collapsed subprocess and document its partial-save
case separately. Model current and proposed Add behavior separately.
Link session use cases and BR-02. BPMN reference: [R1].

DIA-03 UML sequence: inline creation and session save -- P1
Question: in what order do browser, API, and database interact?
Show optional system creation, optional campaign creation, session save,
responses, errors, and refresh. Highlight separate requests/commits; do not
invent a transaction spanning them. Link GAP-03 and related criteria. [R2]

DIA-04 ERD -- P1, parallel drafting dependency, not an agent task
Question: how are systems, campaigns, and sessions related?
Show primary/foreign keys and cardinality: a system can have zero or many
campaigns/sessions; each campaign/session has one system; a session has zero
or one campaign; a campaign has zero or many sessions. Add the named-one-shot
constraint and deletion guard as notes. Link dictionary and BR-01.
This is a data model, not a substitute for BPMN or a UML use case diagram.

DIA-05 UML activity: date selection -- P1/P2
Question: how do open, navigate, choose, dismiss, and save interact?
Focus on picker state and selected value, rather than repeating the whole
session process. Include month/year boundary and invalid/empty-date paths
where applicable. Link GAP-05 and date acceptance criteria. [R2]

DIA-06 UML use case overview -- P2
Question: what goals can the single owner accomplish?
Show manage sessions, campaigns, systems, review calendar/statistics, and
export. Separate future capabilities visually or in a second view. Use cases
represent goals, not a diagram of every tab, click, or API endpoint. [R2]

DIA-07 UML state: campaign lifecycle -- P2, small
Question: what changes when a campaign is archived?
Show Active <-> Archived and deletion from either only when no linked sessions
exist. Treat deletion as termination/removal, not a stored database state.
Do not invent Draft/Completed session states absent from the model. [R2]

DIA-08 BPMN: initial seed migration and reconciliation -- P2
Question: how is source history transformed and checked before reliance on it?
Separate implemented startup import from a proposed review/reconciliation step.
Show normalization, classification, load, failure, and count/data comparison.
Label the reset/reimport administration flow planned if added later. [R1]

DIA-09 Logical component/deployment sketch -- optional P3
Question: how do browser, FastAPI, and SQLite fit together?
Show current local arrangement and intended Compose volumes as distinct views.
No full class diagram is needed in addition to the ERD for this small model.

Notation and review guidance
Use BPMN for process flow and UML for selected software views. BPMN sequence
flows stay within a pool; message flows represent communication between pools.
Use genuine BPMN symbols when drafting, rather than labeling a generic flowchart
"BPMN". UML sequence/activity/use case/state diagrams answer different questions.
References: OMG BPMN 2.0.2 [R1] and OMG UML 2.5.1 [R2]. Tool choice is deferred;
readability, editable source, and a legible exported view are the requirements.

G. QUALITY, TRACEABILITY, AND ANONYMIZATION CONVENTIONS
==========================================================================

IDs: BR business need; FR functional requirement; RULE business rule;
US user story; UC use case; AC acceptance criterion; NFR quality requirement;
DIA diagram; DEC decision; GAP unresolved item; VAL validation evidence.
Use stable sequential IDs. Do not renumber established IDs when reorganizing.

Suggested record fields
Requirement: ID | wording | rationale | priority | implementation status |
evidence/source | related rules | acceptance IDs | open gaps.
Decision: ID | decision | rationale | source/date if known | consequences |
status | supersedes. Do not infer decision dates from later commit dates.
Validation: ID | criteria | environment/data | expected | actual | date |
pass/fail/not run | evidence reference.

Minimal traceability matrix (populate next; this is its structure):
Business need -> FR/NFR -> RULE -> US/UC -> AC -> DIA -> VAL -> GAP/DEC.
Not every requirement needs every artifact. Use "not applicable" deliberately.
Code references support implementation evidence; they do not prove user value
or formal acceptance. Diagram details should reference the same requirements.

Completion rule for each future deliverable
1. Purpose, scope, status and baseline are stated.
2. Sources are identified and assumptions/proposals labeled.
3. Terms, IDs, rules and diagrams agree with related sections.
4. Relevant normal/error/boundary cases are covered.
5. Open issues have a resolution action, not a silently guessed answer.
6. Examples are anonymized; acceptance results are not invented.
7. One review pass completed; any owner decisions still pending are visible.

Anonymization policy
- Owner is "Tracker Owner"; DM1 represents the owner in synthetic examples.
  Use DM2, DM3 consistently for other GMs; explain DM = GM in the glossary.
- Use Campaign 1, Campaign 2; System 1, System 2; One-shot 1; Player 1 where
  needed. Keep equal labels equal across examples, diagrams and criteria.
- Use synthetic notes, dates, links (example.com), and datasets. Preserve
  intended relationships and calculation edge cases, not identifying content.
- For encoding checks use invented Unicode text, not original campaign names.
- Do not include raw exports, personal paths, GM names, private URLs, notes,
  or identifiable screenshots in public-facing documentation.
- Do not modify real application data as part of documentation anonymization.
- Do not put a mapping back to real identities in this portfolio file.
- History references use project-relative paths and commit IDs; any future
  code screenshot must redact hardcoded personal values.
